## 2. Charter Purpose and Authority

This Charter defines the currently documented project direction, scope,
governance, lifecycle, constraints, risks, dependencies, and release posture
for BlockWaveLab V2.

It is a governance draft. It is not a new business decision, requirements
specification, architecture replacement, implementation authorization, or
production approval. Detailed requirements remain in
[BLOCKWAVELAB_SRS.md](../BLOCKWAVELAB_SRS.md); detailed architecture remains in
the architecture and domain documents.

Status labels used in this Charter:

- **APPROVED** — explicitly established by an approved business or governance source.
- **DOCUMENTED** — recorded in project documentation but not necessarily approved as a new baseline.
- **PROPOSED** — described as a future design or recommendation; not authorized by this Charter.
- **UNRESOLVED** — conflicting or insufficiently decided.
- **DEFERRED** — intentionally postponed.
- **BLOCKED** — cannot be completed or verified because a prerequisite is unavailable.
- **HISTORICAL** — evidence from an earlier phase or point in time.
- **NOT VERIFIED** — local or structural evidence exists, but required runtime or deployment evidence is absent.

Implementation evidence labels:

- **LOCAL** — present in the repository.
- **STRUCTURALLY VERIFIED** — supported by source, migration, or static inspection.
- **REMOTE VERIFIED** — confirmed against the linked deployed environment.
- **RUNTIME VERIFIED** — exercised against a configured runtime.

## 3. Executive Summary

BlockWaveLab V2 is documented as an **AI Automation and DevOps Partner for
Web3 Projects**. It is intended to help Web3 teams establish technical
foundations, automate bounded delivery and operations work, operate agreed
technical environments, and connect technical readiness with trust-oriented
growth systems.

The approved service model has four pillars: BUILD, AUTOMATE, OPERATE, and
GROW. The documented engagement model separates one-time implementation from
optional separately paid ongoing service. Observation is part of paid
implementation and is not free support or free monitoring.

The repository contains substantial public website, identity, tenancy,
catalog, commercial, payment-boundary, entitlement, and delivery-foundation
work. The current project is **NOT production-release approved**. Implementation
and foundation work substantially exist, but production release remains
blocked pending runtime verification, provider verification, operational
evidence, and unresolved governance decisions.

## 19. Architecture Principles and Technical Constraints

### Principles — APPROVED/DOCUMENTED

- Preserve the existing public Vite/React/TypeScript foundation.
- Prefer a modular monolith before microservices.
- Separate public content from authenticated data and authorization.
- Reuse Supabase/Postgres, Auth, RLS, trusted functions, and audit foundations.
- Enforce tenant ownership server-side and in database policy.
- Do not trust client-provided organization or project IDs.
- Keep provider integrations behind adapters.
- Preserve immutable snapshots and append-only history.
- Use forward-only migrations.
- Require explicit state transitions, idempotency, concurrency checks, and auditability.

### Current technical constraints

- Existing public routes and SEO behavior must be preserved.
- Browser clients must not receive provider secrets or service-role credentials.
- Sensitive commercial, payment, entitlement, and delivery writes must not be direct browser writes.
- Local migration or source evidence does not prove remote or runtime state.
- Existing domains and lifecycle tables must not be duplicated without approval.

## 20. Security, Privacy and Compliance Principles

The following are documented security constraints:

- RLS and server-side authorization must enforce tenant and project isolation.
- Sensitive operations require trusted functions with fixed search paths and restricted grants.
- Provider webhook signatures must be checked against the raw request body.
- Missing provider configuration must fail closed.
- Browser redirects cannot mark payment successful.
- Session recovery and invitations must not disclose protected account information.
- Secrets, tokens, credentials, and unnecessary personal data must not be logged.
- Immutable commercial records must not be modified through ordinary client access.
- Negative authorization, cross-tenant, replay, and runtime tests are required before production claims.

Privacy, retention, identity-assurance, acceptance-evidence, and regulatory
requirements remain **UNRESOLVED** pending legal/privacy ownership.

## 32. Change Control and Documentation Governance

The documentation architecture defines the following governance model:

```text
Business → Architecture → Code → Database / Runtime / Infrastructure
```

Business decisions are authoritative for business behavior; architecture is
authoritative for approved design intent; source code and migrations are
authoritative for local implementation; deployed/runtime evidence is
authoritative for current execution; historical reports are authoritative
only for the evidence and time they explicitly cover.

Changes to this Charter require:

1. A new version.
2. A recorded change-log entry.
3. Review against the document register.
4. Explicit preservation or resolution of conflicts.
5. Evidence labels for implementation and release claims.
6. Owner approval before changing DRAFT or BASELINED status.

The document register and change log templates exist under
[docs/00-governance/](../00-governance/) but are not populated by this draft.

## 33. Traceability Strategy

Future traceability shall follow:

```text
Business Goal
→ Product Capability
→ Service
→ Requirement
→ Architecture
→ Implementation
→ Test Evidence
→ Release Decision
```

Each relationship should identify the source document, stable identifier,
status label, owner, and evidence location. Unsupported relationships must
remain blank or be marked unresolved. The Charter does not populate service
relationships that depend on the unresolved ten-versus-five catalog conflict.

The detailed SRS remains the requirements traceability source. The
[traceability matrix template](../00-governance/traceability-matrix.md) is
available for future population.
